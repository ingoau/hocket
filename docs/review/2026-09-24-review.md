## Top issues to fix first

1. **CRITICAL — LAN credential harvest.** Any LAN host can win the election by advertising a matching scope hash with a huge revision, and the engine then sends the Subsonic token+salt in a cleartext `Hello`. LAN rooms never verify peers. (`connect/engine.rs:1396`, `election.rs:33`, `discovery.rs:104`.) Fix: never send the credential on LAN tiers; add mutual auth before any document/lease exchange.
2. **HIGH — Unauthenticated LAN peers join rooms**, read the whole session, inject ops, steal the lease. (`connect/room.rs:409`.)
3. **HIGH — Coordinator SSRF**: unauthenticated `Hello.server_url` is fetched server-side with redirects followed, forwarding an honest user's token. (`hocket-coordinator/src/lib.rs:100`.)
4. **HIGH — Desktop IPC `fileRead`/`fileWrite`** let the renderer read/write any path; `hocket-art://` serves all of `userData` including `credentials.json` and the SQLite DB. (`desktop/src/main/ipc.ts:118`, `index.ts:267`.)
5. **HIGH — Path traversal via server-supplied `suffix`** in download file names → arbitrary file write by a malicious server. (`downloads/mod.rs:587`.)
6. **HIGH — Native-API login sends the plaintext password** on every probe, over `http://` if that is the base URL, following cross-host redirects. (`subsonic/native.rs:83`, `probe.rs:75`.)
7. **HIGH — Android FGS start on every launch** with no guaranteed `startForeground` → timeout crashes and a restart loop. (`PlaybackServiceConnection.kt:36`.)
8. **HIGH — Android replays `AddServer` on every `RequestSnapshot`** (three times per launch) and sign-out resurrects the server with full credentials. (`CoreHost.kt:95`, `SettingsScreen.kt:189`.)
9. **HIGH — Outbox replay after crash duplicates** playlists, playlist rows and scrobbles. (`outbox/mod.rs:430`.)
10. **HIGH — Playlist undo** re-enters the public handler (breaks redo, no CAS) and undo of an append-style add silently does nothing while toasting "Undid". (`core/handlers/library.rs:494`, `:337`.)
11. **HIGH — Password/token in logs** at trace level and in `reqwest` error Display; wire `Credential` derives `Debug` unredacted. (`command.rs:10`, `coordinator lib.rs:127`, `wire.rs:130`.)
12. **HIGH — Desktop passwords with a fixed key** on Linux without a recognised keyring (`basic_text` backend). (`credentials.ts:253`.)
13. **HIGH — Concurrent pin jobs corrupt a shared download** (same `.part` file, both marked done). (`downloads/mod.rs:599`.)
14. **HIGH — Android offline launch** leaves the server without an API client, so pinned downloads cannot play. (`servers.rs:70`, `playback.rs:23`.)

Cross-cutting themes: `Shutdown` is fire-and-forget on both platforms (state loss on quit); the stream cache is never populated; outbox/jobs are never pruned; `Debug` on credential-bearing types; several "silent fallback to FakeCore" paths in release builds.

## 1. CRITICAL — Any LAN host can win the election and harvest a permanent Subsonic credential plus the whole session

**Where:** `connect/engine.rs:1396-1402` (`on_connected` sends `self.cfg.credential` in `Hello` for *every* remote tier), `engine.rs:1471-1489` (`on_peer_discovered` accepts any advert whose `scope_hash` matches), `connect/election.rs:33-40` (highest `serving`, then highest `session_revision` wins), `connect/discovery.rs:104-111` (`PeerAdvert::urls` are always `ws://`), `connect/transport.rs:194-235` (plain-TCP `LanListener`, no TLS), `core/handlers/session.rs:97-101` (`verify_lan_peers` is never set; only `coordinator_url`/`lan_enabled`).

**What goes wrong:** the mDNS TXT record carries `scope` = md5 prefix of `url|username` (`discovery.rs:54-58`). An attacker on the same LAN copies that hash from the victim's own advert, advertises `_hocket._tcp` with `serving=1`, `rev=4294967295`, `proto=1`, and a port. Every victim device of that scope runs `on_peer_discovered` → `reevaluate` → `elect_id` picks the attacker → `Output::Connect{ws://attacker:port/}` → `on_connected` sends `Msg::Hello{credential: Some(Credential{server_url, username, token, salt})}` in cleartext. A Subsonic `token`/`salt` pair is valid forever (no nonce), so the attacker now has full Navidrome access as that user. The attacker's room then answers `Welcome{replica: None}` and receives the victim's whole document via `SessionOp::Replace` (`engine.rs:1878-1883`), can inject ops, grant/steal the lease, push `SettingsSync`, etc. The credential is also handed to a *legitimate* LAN leader (another user's laptop on a shared account) although LAN rooms never verify it.

**Fix:** never put the credential in a LAN `Hello` (only when `remote.tier == ConnectionTier::Coordinator`, and only over `wss://`). For LAN rooms add mutual authentication (e.g. HMAC challenge/response keyed from the Navidrome password or a pairing secret) before any document/lease exchange; treat an unauthenticated LAN leader as untrusted.

```rust
// engine.rs on_connected
let credential = match r.tier { ConnectionTier::Coordinator => self.cfg.credential.clone(), _ => None };
```

## 2. HIGH — Unauthenticated LAN peers can join a room, read the replica, inject ops and take transport

**Where:** `connect/room.rs:409-443` (`on_hello`: only `scope` string equality and `max_members` are checked when `cfg.verify` is false), `engine.rs:544-547` (`room_cfg.verify = cfg.verify_lan_peers`, always false in production), `transport.rs:196` (listener binds `0.0.0.0`), `room.rs:496-508` (`Welcome` includes the full `ReplicaState`: document, saved queues, settings, device list, scrobble log), `room.rs:721-738` (`LeaseClaim{takeover:true}` always wins).

**What goes wrong:** with the plaintext scope `https://music.example|alice` (server URL and username are not secrets on a LAN), any host connects to the serving device's listener and is admitted with any `DeviceInfo.id`; it receives the whole session, can `Replace` the document, clear the queue, steal the lease (stopping playback on the real owner via `LeaseFenced`), kick a device by reusing its device id (`room.rs:465-481`), or push `SettingsSync`/`SavedQueuesSync` that the actor applies (`engine.rs:1783-1796`, `core/handlers/connect.rs:220-233`). No hostile-peer scenario exists in the sim.

**Fix:** same as #1 (LAN authentication); at minimum default `verify_lan_peers = true` with the verify proxy, and bind the listener to the interfaces mDNS advertises rather than `0.0.0.0`.

## 3. HIGH — Coordinator SSRF: unauthenticated clients make the server GET arbitrary URLs (and follow redirects) with the presented token

**Where:** `hocket-coordinator/src/lib.rs:100-131` (`App::verify`: `base = credential.server_url` unless `--verify-url`; `format!("{base}/rest/ping.view")`, `.query(&params)`), `lib.rs:80-83` (client built with only a 10 s timeout: default redirect policy = follow 10, no scheme/host restriction), same pattern in the app's LAN role `core/io.rs:116-134`. The Docker `CMD` (`Dockerfile:26`) does not set `--verify-url`.

**What goes wrong:** before any authentication, a `Hello` with `credential.server_url = "http://169.254.169.254/latest/meta-data"` (or `http://localhost:9090`, `http://user:pass@internal`) makes the coordinator issue that request (path fully controlled since only trailing `/` is trimmed; a `#` in the URL discards the appended path). The response body is read fully into memory via `resp.json()` (bounded only by 10 s × bandwidth). Because redirects are followed and reqwest keeps the query string, an honest user's `token`/`salt` is also forwarded to whatever host their server (or a MITM on `http://`) redirects to. The JSON status is also a 1-bit oracle for internal hosts.

**Fix:** make `--verify-url` mandatory (or an allow-list of server hosts); reject non-`http(s)` schemes, userinfo, and private/loopback/link-local IPs after DNS resolution; set `redirect(Policy::none())` and cap the body (`Content-Length`/`bytes()` with a limit, e.g. 64 KiB).

## 4. HIGH — Unauthenticated clients create rooms and replica files on disk for arbitrary scopes (no bound)

**Where:** `lib.rs:161-170` (`attach_sender` → `open_room` on the first `Hello`, before any verification; `open_room` does a synchronous `store.load`), `lib.rs:201-215` (`drive`: when `senders` becomes empty, `store.save(scope, replica)` unconditionally), `lib.rs:354-370` (after a `Close` the socket loop breaks and calls `drive(Disconnected)` which *re-opens* the room from disk and saves it again), `connect/replica.rs:287-312` (`FileReplicaStore::save` writes `<md5>.replica.json` per scope, pretty JSON), `replica.rs:22` (30-day TTL before `purge_expired` removes it).

**What goes wrong:** each `Hello{scope: random}` from an unauthenticated socket (refused for missing credential or scope mismatch) results in: room created, refuse, `Close`, save → file written; then `Disconnected` → load + save again. One attacker loop creates millions of ~1.5 KB files (inode/disk exhaustion) that persist 30 days, and the hourly purge (`lib.rs:414-424`) reads every one of them. All of this happens under the global `rooms` mutex.

**Fix:** only create/persist a room once a member has been *admitted* (e.g. `RoomState.admitted: bool`, skip `save` when the replica was never touched by an admitted member / `doc_is_trivial && devices.is_empty()`); do not reopen a room just to deliver `Disconnected` for an unknown peer; add per-IP rate limiting on `/ws`.

## 5. MEDIUM — No frame-size limit, no connection cap, no read timeout: slowloris and memory DoS on the coordinator (and on LAN listeners)

**Where:** `lib.rs:288-297` (`ws_upgrade` uses `WebSocketUpgrade` defaults: 64 MiB messages / 16 MiB frames per axum 0.8.9), `lib.rs:300-320` (`stream.next().await` with no timeout; an outgoing `mpsc::unbounded_channel` per socket), `lib.rs:354-363` (the "room closed us" check only runs *after* the next inbound frame; after the writer sends `Close`, a peer that never replies keeps the reader blocked forever), `connect/room.rs:964-973` (`unknown` timeout only exists once a room exists, i.e. after a `Hello`; pre-Hello sockets are never timed out), `transport.rs:147-190` and `:214-222` (LAN `pump`/`accept_async` use tungstenite defaults too, so a LAN peer can push 64 MiB frames at a phone).

**What goes wrong:** thousands of idle TCP connections that never send `Hello` (or ignore `Close`) are held open indefinitely; a single member can send a 64 MiB `Op{Replace{document}}` that is parsed twice (`Value` then typed, `wire.rs:77-89`), stored in the replica, broadcast to every member and pretty-printed to disk on every subsequent heartbeat (see #9). `/health` and everything else share the runtime.

**Fix:** `ws.max_message_size(1 << 20).max_frame_size(1 << 20)`; wrap reads in `tokio::time::timeout(MEMBER_TIMEOUT)`; cap concurrent connections (`Semaphore`) and unverified sockets; after `RoomOutput::Close`, abort the reader rather than waiting for the peer.

## 6. MEDIUM — Token+salt written to logs on ping failure; wire `Credential` is `Debug` without redaction

**Where:** `lib.rs:127-129` and `core/io.rs:129-131` (`debug!(%url, error = %e, "ping failed")`). `reqwest::Error`'s `Display` appends ` for url (<full url>)` including the query string (`reqwest-0.12.28/src/error.rs:266-268`; there is no query redaction), so on a connect error/timeout the line contains `u=alice&t=<token>&s=<salt>` — a permanently replayable credential. `connect/wire.rs:130-145` derives `Debug` on `Credential` (unlike `subsonic/auth.rs:49`, which redacts), and it sits inside `Msg::Hello`, `Input::WireIn`, `RoomInput`, `RoomOutput::Verify`, `Output::VerifyCredential`, all `Debug`; the sim's violation dump prints `engine {:?}` (`sim/world.rs:1013-1016`) and `Command` (which carries `AddServer{password}`) is traced with `?cmd` in `core/handlers/command.rs:10`.

**Fix:** log `e.without_url()`; implement `Debug` for `wire::Credential` manually (`token: "<redacted>"`, `salt`, `api_key` likewise); drop the `?cmd` trace or redact `AddServer`.

## 7. MEDIUM — Coordinator URL may be `ws://`/`http://`; the credential is minted once and reused forever, so any coordinator (or on-path attacker) gets permanent server access

**Where:** `settings/registry.rs:222-234` (`url_valid` accepts `ws|wss|http|https`; the engine passes the string straight to `connect_async`, `transport.rs:120-131`), `core/handlers/servers.rs:617-628` (`wire_credential` makes one `token`/`salt` at install time; it is sent verbatim in every `Hello`, `engine.rs:1090-1102`), `docs/design.md` "Coordinator auth: never holds credentials itself".

**What goes wrong:** a user typing `ws://coordinator.example/ws` sends the same replayable `token`/`salt` on every reconnect in cleartext; a hostile coordinator operator, or anyone who reads its debug log (#6), can act as the user against Navidrome indefinitely (Subsonic token auth has no expiry or channel binding). This contradicts the spirit of "the coordinator never holds credentials".

**Fix:** restrict `connect.coordinatorUrl` to `wss://` (allow `ws://` only for loopback/private addresses with an explicit unsafe flag); when Navidrome's `apiKeyAuthentication` lands, send a scoped key; consider proving possession instead of handing over the token (e.g. coordinator issues a nonce that the client mixes into the `salt`, so the pair is single-use for the coordinator: `salt = nonce + random`, then the token is still replayable by design of Subsonic — document this as an accepted risk if not fixed).

## 8. MEDIUM — A LAN group that later reconnects to the coordinator files spurious "session moved on" saved queues and can lose the LAN session's progress

**Where:** `engine.rs:2171-2175` (`on_op_ack` sets `sync_base` whenever `is_connected()`, which is true for the LAN tier), `engine.rs:1891-1940` (`on_welcome`: `fast_forward` needs `sync_base == (room sid, room rev)`; `behind` needs `doc.revision <= rd.revision`; otherwise `FilePreviousStateAsSavedQueue` + adopt), `engine.rs:2207-2228` (leader's later `OpReject{Stale}` after a follower moved the coordinator files *its* state too).

**What goes wrong:** devices A (leader) and B share a session at coordinator revision M, lose the coordinator, continue on the LAN to revision N > M (A's `unsynced` fills, B's `sync_base` = (sid, N)). When the coordinator returns, B connects first: room at M, B at N with `sync_base` rev N ≠ M → not fast-forward, not behind → B files "session moved on while this device was away" and adopts M. If B then makes one op (M+1), A's fast-forward replay is rejected `Stale` → A files "offline changes could not be replayed". Net: the LAN session is demoted to two saved queues and the live queue reverts to M. The sim `Topology` is either `Coordinator` or `Lan` (`sim/world.rs:51-56`), so this transition is untested.

**Fix:** only the device whose room *was* the authority should replay: followers should not record a LAN leader's revisions as `sync_base` (keep the last coordinator sync point) and should treat the leader's replay as the source of truth (e.g. on coordinator `Welcome`, if `lan_leader()` was set and the leader is present, adopt without filing; or have the leader push a single `Replace` and followers reconcile as "behind"). Add a sim topology `LanThenCoordinator`.

## 9. MEDIUM — Global mutex held across synchronous file writes on every heartbeat/op; replica rewritten every 5 s per playing room

**Where:** `lib.rs:181-231` (`drive` holds `rooms` (`parking_lot::Mutex`) while `store.save` does `write` + `rename`), `room.rs:702-715` (`LeaseHeartbeat` sets `dirty = true` → `ReplicaChanged` every 5 s), `room.rs:680-683` (any play/pause/track change), `lib.rs:262-267` (`tick_all` every second under the same lock per room), `lib.rs:393-400` (ticker runs on the tokio runtime; blocking I/O stalls all socket tasks).

**What goes wrong:** with a few hundred rooms the coordinator serialises every WebSocket frame behind disk I/O; a slow disk (Docker volume) turns every heartbeat into head-of-line blocking for all users; combined with #5 a large document makes each write expensive. Design says write cadence is "track change, queue mutation, play/pause, plus heartbeat" — the heartbeat writes are the bulk and only update `expires_at`.

**Fix:** per-room locks (`DashMap`/`Mutex<RoomState>` per scope) and move `save` to `spawn_blocking` with debounce (coalesce writes within ~1 s; write heartbeat-only changes at most every ~30 s since a restart inside the 20 s window is the only thing they buy).

## 10. MEDIUM — Owner-only ops are accepted without an epoch: fencing of `TrackEnded`/`SkipUnavailable` is opt-in by the sender

**Where:** `room.rs:560-576` (epoch is checked only `if let Some(e) = epoch`), `wire.rs:469-475` (`is_owner_op`), `engine.rs:2112-2116` (the honest engine sends `epoch` only when it currently `held`s the lease).

**What goes wrong:** the room is supposed to be "one implementation of every protocol rule"; any peer (or a buggy/old client whose actor still fires `TrackEnded` after `held` became `None`) can push `Op{op: TrackEnded, epoch: None}` and the room advances the queue for everyone, defeating the split-brain protection the epoch exists for. Today the actor gates on `owns_transport()` (`core/handlers/playback.rs:583-585`), so only hostile/desynced peers hit it.

**Fix:** in the room, `if op.is_owner_op() { let Some(e) = epoch else { reject Fenced }; check(...) }`.

## 11. LOW — Room relays client-claimed `device_id`s instead of the member's identity

**Where:** `room.rs:551-621` (`Op.device_id` is echoed into `OpCommitted` unchanged; the lease check uses the member's id but the broadcast uses `op_device`), `room.rs:878-900` (`ScrobbleSubmitted`/`ScrobbleDedupeQuery.device_id` from the frame), `room.rs:812-830` (`HandoffReady.from`), `engine.rs:2024-2027` (op ids are predictable `"<device>-<n>"`), `engine.rs:2245-2247`.

**What goes wrong:** a same-scope peer can claim another device's id in `ScrobbleDedupeQuery` so the log records the pair as that device; the real device's later query returns `Own` → both submit → duplicate scrobble. Or it can commit an op as `device_id: victim, op_id: "victim-<next>"` so the victim treats the commit as its own pending op and skips applying it, then diverges until a resync. Impact is limited to devices of the same user, but it makes the dedupe log unreliable.

**Fix:** overwrite `device_id`/`from` with `me.device.id` in the room before recording/relaying.

## 12. LOW — `max_members` ignores pending/unknown sockets; those lists are unbounded

**Where:** `room.rs:417-441` (cap checked against `members` only), `room.rs:122-124`, `room.rs:434-441` (`pending` grows per verifying socket), `room.rs:245-247` (`unknown`).

**What goes wrong:** N sockets can all be in `pending` at once and all be admitted past `max_members` when their verifications return; `unknown`/`pending` grow with connection count (see #5).

**Fix:** count `members + pending` against the cap and cap `unknown`.

## 13. LOW — Replica grows without bound from authenticated members (devices, saved queues, settings) and is shipped in every `Welcome` and every disk write

**Where:** `replica.rs:76-100` (`touch_device` adds an entry per distinct `DeviceInfo.id`, pruned only after 7 days), `wire.rs:811-850` (`merge_saved_queues`/`merge_settings` are add-only LWW; nothing ever deletes), `room.rs:904-923` (every `SavedQueuesSync` that adds anything is rebroadcast to all members), `room.rs:498` (`Welcome` clones the whole replica).

**Fix:** cap `devices` (e.g. 64, evict oldest `last_seen`), cap saved-queue/settings entries or require tombstones; reject saved queues above a size.

## 14. LOW — Handoff: source releases transport before the room confirms; a vanished target leaves dead air with no signal back

**Where:** `engine.rs:2644-2666` (`handoff_to` sends `HandoffTakeover`, then immediately `held = None`, `Output::ReleaseTransport`), `room.rs:842-845` (`if !self.has_member(&target) { return; }` silently), `room.rs:872-874` (Fenced → only `LeaseFenced` to the source, which has already released).

**What goes wrong:** the target disconnects between the picker's presence update and the takeover: the source stops playing, the room drops the request, nobody plays, no UI feedback. Design says "the handoff doesn't fail, playback doesn't stop".

**Fix:** have the room answer with a `HandoffTakeover{lease: None}`/`Bye`-style failure so the source re-claims (`claim(None, true)`) and resumes; or release locally only on `LeaseGranted{owner: target}`.

## 15. LOW — Replica files are not fsync'd; the `.tmp` name is shared per scope

**Where:** `replica.rs:301-312` (`std::fs::write(&tmp)` + `rename`, no `sync_all`, no directory fsync).

**What goes wrong:** after a power loss the rename can be durable while the content is not (zero-length or partial file) → `load` fails → `warn "could not load replica; starting fresh"` (`lib.rs:172-178`) and the resume point is lost; acceptable for a cache but worth a `sync_all()` given the file is small.

## 16. LOW — Scrobble dedupe knowledge on devices is memory-only; leadership moves after a restart lose it

**Where:** `engine.rs:491-494, 1064-1076` (`known_scrobbled`, cap 500, not persisted), `engine.rs:1079-1088` (own room seeded from it on every `attach_loopback`), `replica.rs:24-28` (24 h TTL / 500 cap on the room side), `sim/tests.rs:314` (crash/restart test runs on the coordinator topology only).

**What goes wrong:** on the LAN tier, if the leader restarts (app killed) and is re-elected, its room's dedupe log is empty; a follower that reached 50% on a track handed over before the restart asks the new room and gets `New` → duplicate scrobble. Design calls dedupe "optional", but the sim invariant "no scrobble duplicated" is only exercised without a LAN restart.

**Fix:** persist `known_scrobbled` with `PersistedConnectState` (it is small) and seed the room from it; add a LAN crash/restart sim scenario.

## 17. LOW — Election spoof/flood surface: `lan_peers` never pruned except on `PeerLost`; adverts with any `rev`/`serving` are trusted

**Where:** `engine.rs:1480-1488`, `election.rs:33-40`, `discovery.rs:79-97` (`from_txt` parses `rev`, `serving` from TXT).

**What goes wrong:** beyond #1, an mDNS flood with many device ids grows `lan_peers` and causes a reevaluate/reconnect churn (`reevaluate` → `drop_remote` → `attach_loopback` each time the winner changes), interrupting the upstream repeatedly (`engine.rs:1199-1228`).

**Fix:** cap `lan_peers`, rate-limit re-election (hysteresis: don't switch away from a working upstream unless the current leader is lost), ignore `rev` from unauthenticated adverts once LAN auth exists.

## Test gaps that matter

- Coordinator: `tests/handoff.rs` covers one happy handoff. Nothing exercises refusal paths (missing credential, scope mismatch, verify failure/timeout), that refused sockets are closed and nothing is persisted (#4), `max_members`, oversized frames (#5), or restart-from-disk lease handling.
- Sim: no hostile peer, no `Lan → Coordinator` transition (#8), no LAN leader restart (#16), no test that `Hello` to a LAN leader omits the credential (#1). Invariant 1 deliberately excludes detached owners, so "two devices audibly playing during a partition" is accepted, not measured.
- Room: no unit test that owner-only ops without `epoch` are rejected (#10) or that `device_id` in frames is ignored (#11).

## Notes (not findings)

- Path traversal via scope is not possible: `FileReplicaStore::path_for` hashes the scope (`replica.rs:262-268`).
- Clock math is all `f64`; `extrapolate` clamps to `u32::MAX` and never goes backwards (`clock.rs:170-186`); `OffsetEstimator::record` drops `t3 < t0`/non-finite samples; the sim's `to_micros` uses a saturating cast. No i64/u64 conversions found in the protocol path.
- Reconnect backoff is bounded (1 s → 30 s cap, `transport.rs:75-96`); `Refuse{Unauthorised}` skips ahead 4 steps. A stale credential after a password change is pushed to the engine via `Input::SetCredential` (`servers.rs:181`), so the loop self-heals.
- Revision arithmetic uses `saturating_add`; wrap at `u32::MAX` would stall commits but is unreachable in practice.
- TLS: `tokio-tungstenite` with `rustls-tls-webpki-roots`, certificate validation on; no way to trust a self-signed coordinator certificate (usability, not security).

## HIGH

### H1. Path traversal: server-supplied `suffix` is used verbatim as a file extension for downloads
**Files:** `downloads/mod.rs:587-591` (`download_path`), `downloads/mod.rs:639` (`fetch_track`), `downloads/mod.rs:705-716` (`cache_path`), `subsonic/transport.rs:186-204` (`download` creates parent dirs, writes `.part`, renames), `subsonic/convert.rs:92` (suffix copied from `Child.suffix`).

`safe_name()` sanitises the track id but the `ext` half of `format!("{}.{}", safe_name(track_id), ext)` comes straight from the mirror's `tracks.suffix`, which is whatever the server put in `Child.suffix`. A malicious or compromised server (or a MITM on an `http://` base URL, which is accepted, see M1) can return `suffix = "../../../../some/dir/evil"`. `PathBuf::join("abc.../../../../some/dir/evil")` yields a path with `..` components; `ReqwestTransport::download` then does `create_dir_all(parent)` (which creates `abc..` and walks up), writes `evil.part` and renames to `evil`. Result: arbitrary file write (with server-controlled bytes) anywhere the app can write, e.g. into Android `shared_prefs`/databases or the Electron userData dir; `pin_tracks.path` then records that path and `unpin`/`reconcile_playlist` will `remove_file` it later (`downloads/mod.rs:324, 515`).

**Fix:** sanitise the extension the same way as the id (`[A-Za-z0-9]{1,8}` else `bin`), and in `ReqwestTransport::download` refuse a `dest` that is not a plain file name under the expected directory (check `dest.components()` contains no `ParentDir`/`RootDir`, or canonicalise the parent and assert it starts with the download root).

### H2. Native-API login sends the plaintext password over whatever transport the base URL uses, automatically, on every probe; redirects are followed
**Files:** `subsonic/native.rs:83-95` (`login` POSTs `{"username","password": password.expose()}`), `subsonic/probe.rs:75-84` (login attempted for every `Password` auth mode, regardless of `serverType`), `core/handlers/servers.rs:34-41` (`Url::parse` only; no scheme check), `subsonic/transport.rs:104-114` (reqwest client with default redirect policy).

The design promises token+salt so the password never crosses the wire, but the capability probe performs a Navidrome-native `/auth/login` with the raw password whenever the account uses password auth. Nothing requires `https://`, so a LAN `http://` server (the common Navidrome setup) leaks the password in cleartext on every connect. reqwest's default policy follows up to 10 redirects, including cross-host and HTTPS→HTTP, and re-sends the body on 307/308; a server (or attacker who controls a redirect) can therefore forward the credentials elsewhere. reqwest strips only `Authorization`/`Cookie`/`Proxy-Authorization` on cross-host redirects, so the custom `x-nd-authorization: Bearer <jwt>` header (`native.rs:131-136`) also follows the redirect to a foreign host.

**Fix:** (a) only attempt native login when `base_url.scheme() == "https"` (or when the host is loopback), and make it opt-in behind the `native_api` need rather than every probe; (b) build the reqwest client with `.redirect(redirect::Policy::none())` (or a custom policy that rejects scheme downgrades and host changes) for both the API client and downloads; (c) reject non-`http(s)` schemes in `add_server`.

### H3. Two pin jobs can download the same track concurrently into the same `.part` file → corrupted download marked `done`
**Files:** `downloads/mod.rs:599-664` (`fetch_track`), `downloads/mod.rs:436-470` (`plan` selects `state IN ('wanted','failed')`; `materialise` only short-circuits on `state='done'`), `core/handlers/servers.rs:336-339` (Download runner concurrency = 2), `subsonic/transport.rs:190-204` (`tmp = dest.with_extension("part")`, unconditional create/rename).

Pin an album and a playlist that contains one of its tracks; both jobs are queued with that track in their item lists, and with concurrency 2 both run. Both call `fetch_track` for the same `(server_id, track_id)`, compute the same `dest`, and both stream into the same `<dest>.part` (`File::create` truncates), then each renames it. The file that ends up at `dest` is interleaved bytes from two writers; both jobs then `UPDATE pin_tracks SET state='done', bytes=<their count>`. The failure branch `remove_file(&dest)` (`:666`) can also delete a good file that the other job just completed.

**Fix:** serialise per track: in `fetch_track` do a compare-and-set `UPDATE pin_tracks SET state='downloading' WHERE ... AND state IN ('wanted','failed')` and skip when 0 rows changed (or keep an in-process `Mutex<HashSet<(sid,tid)>>`); write to a unique temp name (`dest.with_extension(format!("{id}.part"))`) and never `remove_file(dest)` on failure unless this call created it.

### H4. Outbox is at-least-once across a crash: `recover()` re-sends non-idempotent mutations (duplicate playlist, duplicate playlist rows, duplicate scrobble)
**Files:** `outbox/mod.rs:430-437` (`recover` flips `inflight`→`pending`), `:463-478` (claim, then `execute`, then mark `done` in a separate write), `:582-600` (`PlaylistCreate`), `:609-619` (`PlaylistAdd` with `at_index: None` → `songIdToAdd`), `:716-722` (`Scrobble submission=true`), `:848-850` (`db_err` maps DB errors to non-transient `Io`), `core/actor.rs:546`.

If the process dies (or the DB write after the server call fails) between the server accepting the call and `status='done'`, the entry is replayed on restart. `createPlaylist` creates a second playlist with the same name; `updatePlaylist songIdToAdd` appends the tracks again; `scrobble submission=true` submits a second play at the same `time` (Navidrome increments play count per submission). `PlaylistCreate` is worse than a crash: a `DbError` from `upsert_playlists`/`set_playlist_tracks` after the server call is mapped by `db_err` to `SubsonicError::Io`, which is not transient, so the entry goes to `failed` and "Retry pending changes" (`retry_failed`) creates the playlist again. The design invariant is "no scrobble lost or duplicated". Test `network_failure_stops_the_batch_and_recover_resets_inflight` only covers the reset, not the replay semantics.

**Fix:** make replays safe rather than avoiding them: for `PlaylistCreate` record the server id on the entry before any local DB work and, on replay, look for a playlist with that name created after `created_at`; for `PlaylistAdd(None)` fetch the playlist first and skip ids already present (or convert to `replace_playlist` with the rebased order like the `Some(idx)` path); for `Scrobble` treat a replay whose `history_id` row already has `scrobbled=1` as done. Persist `done` in the same transaction as the post-call mirror updates.

## MEDIUM

### M1. `add_server` accepts any parsable URL; a cannot-be-a-base URL panics inside the probe task and leaves the server "connecting" forever
**Files:** `core/handlers/servers.rs:34-41`, `subsonic/client.rs:216-221` (`path_segments_mut().expect(...)`), `subsonic/native.rs:66-68` (same), `core/actor.rs:498-508` (`spawn` increments `in_flight`; `TaskDone` only sent after `fut.await` returns).

`Url::parse("mailto:x@y")` (or `data:`, `javascript:`) succeeds and `cannot_be_a_base()` is true; `rest_url` then panics on the runtime task. No `Internal::Probed` is ever sent, `pending_servers` keeps the entry, `in_flight` is never decremented (shutdown waits), and the UI never gets a result. Also nothing rejects `http://` (see H2) or a URL with embedded userinfo.

**Fix:** validate in `add_server`: scheme in `{http, https}`, `host_str().is_some()`, no username/password in the URL; return `Toast` otherwise. Change `rest_url`/`native_url` to return `Result` rather than `expect`.

### M2. A successful HTTP status is treated as a successful media download; Subsonic error envelopes (HTTP 200 + JSON) are stored as "done" downloads and cached artwork
**Files:** `downloads/mod.rs:641-660` (any `Ok(out)` → `state='done'`, `content_type` stored but never checked), `cache/mod.rs:181-197` (same for `getCoverArt`), `subsonic/transport.rs:162-209`.

Subsonic returns protocol errors (bad token, unknown id, error 70) as HTTP 200 with `application/json`. `download_to_file` only maps 401/403/404/non-2xx, so for `/rest/download` and `/rest/getCoverArt` the JSON error body is written to `<track>.flac` / `<id>_320.img`, marked complete, `offline = Downloaded`, and offered to the player as a local file. The pin looks fully downloaded while the track is unplayable offline; the artwork entry caches a JSON blob until manually cleared.

**Fix:** in `Client::download_to_file`, treat a 2xx whose `content_type` starts with `application/json` or `text/` as an error: read the file, run `parse_envelope`, delete the file and return the typed error. Optionally also reject `bytes == 0`.

### M3. `outbox.prune()` and `jobs.prune()` are never called: outbox, jobs and job_items grow without bound
**Files:** `outbox/mod.rs:440-445` (`prune`, only referenced from tests), `jobs/mod.rs:767-778` (`prune`, only tests), `core/actor.rs:700-721` (housekeeping only calls `caches.meta_prune()`), `core/actor.rs:706-711` (an `OutboxFlush` job is submitted every `OUTBOX_RETRY_MS` while anything is pending).

Every played track produces two `done` outbox rows (now-playing + submission) that are kept forever; every flush and every download produces a `jobs` row plus `job_items`. `Outbox::pending()` / `jobs()` filter by status so the UI stays correct, but the DB file and the durable-table backups grow linearly with listening history, and `flush`'s `ORDER BY created_at` over the whole table gets slower.

**Fix:** call `outbox.prune(7 days)` and `jobs.prune()` in the hourly housekeeping block next to `meta_prune`.

### M4. Design gap: the evictable stream cache is never written
**Files:** `downloads/mod.rs:720-742` (`cache_put`), `downloads/mod.rs:665-760` (`resolve` consults `cache_get`), grep: no caller of `cache_put`/`cache_path` outside `downloads/mod.rs` and its tests.

`resolve()` goes download → cache → stream URL, and the settings/UI expose a cache budget, `ClearStreamCache` and `OfflineState::Cached`, but no production code ever populates `cache_entries` or the `stream/` directory (the native HTTP audio path streams directly). The "night of streaming can't evict an album" separation, the cache budget setting and the `Cached` state are dead in practice; `refresh_offline` can never return `Cached`.

**Fix:** either wire the native backend's stream reader to write completed files through `cache_put` (behind a size check), or drop the cache surface from settings/UI until it exists so users are not shown a budget for something that never fills.

### M5. A panicking job runner leaves the job `running` until the next process start; a panicking actor task leaks `in_flight`
**Files:** `jobs/mod.rs:692-696` (`tokio::spawn { fut.await; drop(permit); q.finish(..) }`), `jobs/mod.rs:640-655` (`running` map entry only removed in `finish`), `core/actor.rs:498-508`.

If a runner future panics (e.g. the `expect` in M1 reached via `download_url`, an index panic in a converter on odd server data), `finish` never runs: the semaphore permit is released, but the DB row stays `running`, the `running` map keeps the id, `has_active(LibrarySync)` stays true so no further sync is ever scheduled, and the UI shows a job spinning forever. `JobQueue::recover` fixes it only at restart.

**Fix:** wrap `fut` in `futures::FutureExt::catch_unwind(AssertUnwindSafe(fut))` and map a panic to `Err(JobError::Failed("panicked"))` before `finish`; similarly in `Actor::spawn`, send `TaskDone` from a `catch_unwind`/`Drop` guard.

### M6. Config import trusts document timestamps and skips the sync path; device-local keys are overwritten wholesale
**Files:** `settings/mod.rs:345-370` (`apply_settings` uses `s.updated_at` from the document), `core/handlers/settings.rs:283-322` (`import_config` calls `apply_setting_side_effects` but never `after_setting_changed`, so no `Input::SettingChanged`), `settings/mod.rs:380-406` (`merge` is LWW on `updated_at`).

A hand-edited or third-party document with `updatedAt: 9e15` on an account-synced key wins every future LWW merge on every device and cannot be overridden by any normal `SetSetting` (whose timestamp is `now`). Conversely, an honest old backup restores synced keys with old timestamps, they are not broadcast (no `SettingChanged` input), and the next merge from any peer silently reverts them, so "Configuration imported" is misleading. Device-local keys (`audio.settings`, output device, `connect.coordinatorUrl`, `transcoding.profiles`, storage budgets) are imported unconditionally, which is defensible for same-device restore but surprising cross-device and there is no scope filter or confirmation.

**Fix:** clamp imported `updated_at` to `min(doc.updated_at, now)`; after import, route synced keys through `after_setting_changed` (or `queue_input(Input::SettingChanged)`) so peers learn about them; consider a flag/UI choice for importing device-local scope.

### M7. Outbox DB failures during `execute` are classified as permanent, and now-playing entries are replayed hours later
**Files:** `outbox/mod.rs:848-850` (`db_err` → `SubsonicError::Io`), `:497-506` (non-transient → `failed`), `subsonic/mod.rs:92-97` (`is_transient` excludes `Io`), `:716-722` (`submission=false` entries retried like any other).

`SQLITE_BUSY`/`LOCKED` from `upsert_playlists`, `set_playlist_tracks` or `mark_scrobbled` after a successful server call marks the entry `failed` with a retry problem; a retry re-sends the server call (see H4). Separately, a `Scrobble { submission: false }` that hits a network blip is retried with backoff (up to 10 min) and then sent as "now playing" for a track that stopped long ago; there is no expiry for now-playing entries.

**Fix:** classify `DbError` as transient (or better, treat "server call done, local write failed" as success and log); drop `submission=false` entries whose `played_at` is older than a few minutes at flush time.

### M8. `fetch_track` failure/interruption leaves `.part` files, and failure deletes `dest` unconditionally
**Files:** `subsonic/transport.rs:190-204` (no cleanup of `tmp` on error), `downloads/mod.rs:666` (`remove_file(&dest)`).

A network error mid-stream returns `Err` from `download`, leaving `<dest>.part` on disk (never counted in `downloads_bytes`, never cleaned, only overwritten by a later attempt for the same track). On the failure branch `fetch_track` removes `dest` even when it did not create it (a previous complete download for a re-planned `failed` row, or the concurrent writer in H3).

**Fix:** delete `tmp` on any error in `download`; in `fetch_track` only remove `dest` when the download outcome says a file was created.

## LOW

### L1. `apply_local` for playlist edits on an unknown playlist writes rows with `server_id = ''`
**Files:** `outbox/mod.rs:1001-1016` (`local_order` returns `""` when the playlist row is missing), `:902-915, 921-947, 949-967`.
Enqueuing `PlaylistAdd/Remove/Move` for a playlist id not yet in the mirror (e.g. right after `PlaylistCreate` before the flush maps the id) inserts `playlist_tracks` rows keyed on an empty server id that no query ever reads and `clear_mirror` never deletes. **Fix:** return early from `apply_local` when the playlist is unknown.

### L2. `unpin` / `reconcile_playlist` abort on the first `remove_file` error
**Files:** `downloads/mod.rs:314-328`, `:503-519`.
The `pin_tracks` rows are already deleted in the preceding transaction; a single EACCES/ENOENT-race aborts the loop, leaving other orphan files on disk and `tracks.offline` stale (`refresh_offline` skipped) with no retry path. **Fix:** collect errors, continue the loop, report once.

### L3. Orphan files when another pin only *wants* the track
**Files:** `downloads/mod.rs:307-313` (orphan query counts any row of another pin, regardless of `state`), `:429-434` (`materialise` copies the path only from `done` rows).
Unpin A while pin B has the same track `wanted` (job not yet run): the file is kept (B "needs" it) but B's row has no `path`, so B re-downloads and the old file is never referenced or deleted. **Fix:** in the orphan query require `state='done'` on the other rows, or copy the path onto B's rows before deleting A's.

### L4. `lyrics.external.enabled` is account-synced
**Files:** `settings/registry.rs:272-274`.
The design calls external lyrics fetch a privacy trade-off ("reveals what you're listening to"). Because the key is `AccountSynced`, enabling it on one device silently enables it on every device via LWW merge, including a shared household desktop. **Fix:** make it `DeviceLocal` (like `connect.*` keys), or at least keep the provider synced but the toggle local.

### L5. `HttpTransport::execute` buffers response bodies with no size cap
**Files:** `subsonic/transport.rs:142-157`, `subsonic/client.rs:301-310` (`parse_envelope`).
`search3` pages or a hostile server can return arbitrarily large bodies which are fully buffered before parsing. Bounded only by the 30 s timeout. **Fix:** stream with a limit (e.g. 32 MiB) and fail with `Protocol`.

### L6. `.part` temp name collides for ids that differ only in extension, and `safe_name` maps all punctuation to `_`
**Files:** `subsonic/transport.rs:190`, `downloads/mod.rs:781-791`, `cache/mod.rs:115-127`.
`with_extension("part")` on `abc.flac` and `abc.mp3` gives the same `abc.part`; `safe_name("a/b") == safe_name("a_b")`. Navidrome ids are hex so the practical risk is low, but it is another reason to use a unique temp name (H3) and an injective encoding (hex/base32 of the id).

## Design-vs-implementation notes (not separately rated)
- `docs/design.md` "Auth: Token+salt … Never plaintext": contradicted by H2 for the native API path.
- "Downloads … evictable stream cache … different directories, different policies": the cache half is unimplemented (M4).
- "no scrobble lost or duplicated": crash-replay duplicates (H4). The handoff dedupe itself is handled in the connect engine (`playback.rs:745-760` routes `Submit` through `Input::ScrobbleReached`), which is outside this area and was not reviewed.
- "Forward-only numbered migrations … backup before migrating": implemented correctly in `db/mod.rs:322-372` (backup via `VACUUM INTO` when `from > 0`, one transaction per migration, mirror drop-and-retry). No issues found.
- Filter SQL (`filters/sql.rs`), FTS query building (`db/queries.rs:268-291`), and all `format!`-built SQL in `db/queries.rs`/`outbox`/`jobs`/`downloads` splice only trusted identifiers/enums; user text is always bound. No injection found. Filter trees are bounded (`MAX_DEPTH=8`, `MAX_NODES=256`, `filters/model.rs:349-406`); NSP import validates through the same path.
- `Credential` zeroises and redacts `Debug` (`subsonic/auth.rs`); no logging of URLs containing `t`/`s`/`apiKey` was found in this area. `random_salt` uses `rand::rng()` (CSPRNG) with 64 bits, fine.

# Core actor / playback / session review

All paths below are relative to `/home/user/hocket/`. Read-only review; nothing was changed or built.

## HIGH

### 1. Undo of a playlist edit re-enters the public handler: pushes a new undo entry and wipes the redo stack
- `crates/hocket-core/src/core/handlers/library.rs:494-500` (`run_cas` fallback arm: `self.handle_command(m.command.clone())`), `library.rs:312-355` (`playlist_add` → `push_remote_undo`), `library.rs:357-402` (`playlist_remove`), `library.rs:404-442` (`playlist_move`), `crates/hocket-core/src/undo/mod.rs:505-540` (`push_from` does `self.redo.clear()` on every push).
- What goes wrong: user does *Add to playlist* (entry A), presses Ctrl+Z. `undo()` pops A onto the redo stack, `perform_undo_action` → `run_cas` → for playlist targets the inverse is executed as `Command::PlaylistRemove` through `handle_command`, which calls `playlist_remove`, which calls `push_remote_undo("playlistRemove", …)`. That push clears the redo stack (A is gone, Ctrl+Y does nothing) and adds a new undoable entry "Remove from playlist" whose own undo is "Add to playlist", and so on. Undo of a playlist edit therefore is never a step back in history; it is a new forward action, and redo is broken for every playlist op. Also, no compare-and-swap happens for playlist inverses at all (the code comment says "the outbox rebases them"), which contradicts design.md "Inverses compare-and-swap … report honestly".
- Fix: give the library handlers an internal entry point that enqueues the mutation without touching the undo stack (e.g. `playlist_add_inner(.., record_undo: bool)`), and call that from `run_cas`. Alternatively route playlist inverses through `outbox.execute_cas` like ratings, comparing the playlist's current order against `expect` before applying.

### 2. Undo of "Add to playlist" (append) silently does nothing but reports success
- `crates/hocket-core/src/core/handlers/library.rs:337-347` (`set: RemoteValue::Member { present: true, index: at_index.map(|a| a + i) }`, so `index: None` when `at_index` is `None`), `crates/hocket-core/src/undo/mod.rs:157-169` (`command()` for `Member { present: false }` needs `from == Member { index: Some(i) }` and returns `None` otherwise), `undo/mod.rs:381-383` (`inverse()` is `filter_map`, so the item is dropped), `library.rs:456-461` (`total == 0` → `finish_cas` → toast "Undid Add to playlist").
- What goes wrong: every `PlaylistAdd` without an explicit index (the common case: context menu "Add to playlist", `SaveQueueAsPlaylist` etc.) produces an `UndoAction::Cas(vec![])`. Ctrl+Z shows "Undid Add to playlist (3)" and the tracks stay in the playlist. Money-equivalent state (design: playlist add/remove are undoable) is silently not undone.
- Fix: in `playlist_add` compute the index for appends from the current order (`order.len() + i`), or make `RemoteItem::command` for `Member { present: false }` fall back to a track-id based removal (`PlaylistRemove` by track id) when no index is known.

### 3. Server password (and stream URLs carrying the auth token) reach the log at `trace`
- `crates/hocket-core/src/core/handlers/command.rs:10` (`tracing::trace!(target: "hocket_core", ?cmd, "command")`), `crates/hocket-core/src/api.rs:1364-1393` (`Command` derives `Debug`; `AddServer { password: String }` is a plain string), `crates/hocket-core/src/audio/external.rs:70` (`tracing::trace!(?command)` on every `BackendCommand`; `MediaSource.url` is documented at `api.rs:1017` as "`https://` stream URL … (auth in query)"), `crates/hocket-node/src/lib.rs:82-90` and `crates/hocket-android/src/lib.rs:76-83` (`init_logging(level)` takes an arbitrary `EnvFilter`; desktop passes `process.env.HOCKET_LOG`).
- What goes wrong: a user asked to run with `HOCKET_LOG=trace` (or `hocket_core=trace`) for a bug report gets their Navidrome password in stderr/logcat in clear text; on Android every `Load`/`SetNext` prints a URL with `u=`, `t=`, `s=` that is a full replayable credential. design.md: "Never plaintext".
- Fix: wrap the password in `subsonic::Credential` at the API boundary (or a newtype with a redacting `Debug`), and log only the discriminant of the command (`std::mem::discriminant`/a `kind()` string). For `BackendCommand`, log the key and a URL with the query stripped.

## MEDIUM

### 4. `Command::Shutdown` is fire-and-forget; both platforms exit/drop the core before the flush runs
- `crates/hocket-core/src/core/actor.rs:373-376` (Shutdown breaks the loop), `actor.rs:567-586` (`shutdown()` does the session flush, `save_position`, settings save, autoplay exclusion save), `crates/hocket-core/src/core/mod.rs:296,353` (the owned runtime is dropped with `Core`), `desktop/src/main/core-host.ts:98-100` (`shutdown()` resolves right after `dispatch`), `desktop/src/main/index.ts:232-238` (`core.shutdown().finally(() => windows.destroyAll())`), `android/core/src/main/java/app/hocket/core/NativeCore.kt:56-58` (`dispatch(Command.Shutdown); core.close()`).
- What goes wrong: the actor task runs `shutdown()` on a runtime worker after the message is received; the caller cannot know when that happened. On Android `core.close()` drops the `Core`, and with it the tokio runtime, immediately after `dispatch`: if the actor hasn't been scheduled yet the Shutdown message is dropped and nothing is flushed. Up to 250 ms of queue changes (`DOC_SAVE_DEBOUNCE_MS`), up to 30 s of position (`POSITION_HEARTBEAT_MS`), the settings document and the autoplay exclusion set are lost. "Flush everything and stop. The process may exit afterwards." (api.rs:1371) is not true as implemented.
- Fix: make shutdown observable: e.g. `Core::shutdown(&self) -> impl Future` that sends `Shutdown` with a oneshot and awaits it (or `Query::Shutdown`), and have the bindings await it before `close()`/`destroyAll()`. Also flush the document on every `mark_doc_dirty` when `!started`-independent `force` conditions (queue mutations are rare enough to write immediately on Android).

### 5. Claiming transport after another device moved the queue on loads the new track at this device's stale position
- `crates/hocket-core/src/core/handlers/session.rs:470-475` (render-only branch sets `doc_key`/`track`/`loaded=false` but leaves `playback.position_ms` untouched), `crates/hocket-core/src/core/handlers/playback.rs:231-246` (`on_lease_changed`: `position = restore_position … .unwrap_or(self.playback.position_ms)`), `playback.rs:389-401` (`ensure_loaded_then_play` same fallback).
- What goes wrong: A owns transport, is paused at 1:30 into track X (or loses the lease at 1:30). B takes over, skips to track Y, then stops/releases (`Stop` → `ReleaseTransport`). Nobody owns. On A the user presses Play: `transport_command` → `ClaimTransport` → `LeaseChanged { owns: true }` → `load_item(Y, 90_000, …)`. Track Y starts 1:30 in. The remote stamp position (`engine.position_ms()`) is available but not consulted here.
- Fix: in the render-only branch reset `self.playback.position_ms = 0` (or to `engine.position_ms()` when the key matches the stamp); in `on_lease_changed`/`ensure_loaded_then_play` only reuse `playback.position_ms` when `playback.doc_key == item.key` and the position was taken for that key.

### 6. `load_item` position clamp is a no-op, so out-of-range positions reach the backend
- `crates/hocket-core/src/core/handlers/playback.rs:141`: `self.playback.position_ms = position_ms.min(track.duration_ms.max(position_ms));` — `min(max(d, p)) == p` for every `p`.
- What goes wrong: a saved queue merged from a peer (LWW, no validation of `position_ms`), an `Effect::PositionRestore`, or `Command::SeekTo { position_ms: 4_000_000_000 }` sent before anything is loaded (`seek_to` at `playback.rs:426-429` stores it unclamped when `!loaded`) is passed verbatim to `backend.load(source, next, position_ms, play)`. The native backend seeks past EOF → immediate `Ended` → `TrackEnded` → the restored track is skipped; `Playback::position_now` then reports a position above the duration until the first `Position` report.
- Fix: `let pos = if track.duration_ms > 0 { position_ms.min(track.duration_ms) } else { position_ms };` and clamp in `seek_to` for the `!loaded` branch too.

### 7. `ExportNsp { path }` writes arbitrary paths with partially user-controlled content, no validation in the core
- `crates/hocket-core/src/core/handlers/library.rs:873-897` (`tokio::fs::write(&p, document.as_bytes())` with `p` straight from the command), `crates/hocket-core/src/api.rs:1585-1590`.
- What goes wrong: the core trusts the UI-supplied path completely (no `..`/absolute check, no extension check, no confinement to a chosen export directory). The written bytes are an NSP JSON whose `name`/rule strings come from the filter the same caller supplied. A compromised renderer (or any process that can reach the IPC bridge) can overwrite any file the app user can write, e.g. dotfiles, with JSON containing attacker-chosen substrings. The design calls out path handling for nsp export/import as a security concern.
- Fix: require the path to end in `.nsp`, refuse paths containing `..`, and either confine to a platform-supplied export directory (config) or require the platform to pass a handle it obtained from a save dialog. At minimum log the resolved absolute path and refuse to overwrite existing non-`.nsp` files.

### 8. Non-owning devices can never "Previous = restart" (Symfonium behaviour) — design gap
- `crates/hocket-core/src/core/handlers/session.rs:692-704`: `if self.playback.loaded && previous_should_restart(position)` — `playback.loaded` is always `false` on a device that does not own transport (`session.rs:474`) and `position` is `playback.position_now` (local, stale), so the `transport_command(SeekTo 0)` branch is unreachable for non-owners.
- What goes wrong: on a laptop controlling the phone, pressing Previous 2 minutes into a track jumps to the previous track instead of restarting, while the same press on the phone restarts. The `TransportRequest(SeekTo)` forwarding path already exists for this case.
- Fix: use `self.transport_state().position.position_ms` (extrapolated remote stamp) and drop the `loaded` condition when not owner.

### 9. `on_document_changed` returns early in the resolve path, skipping persistence and events for that document
- `crates/hocket-core/src/core/handlers/session.rs:490-497`: on `Effect::ResolveContext` it calls `local_op(SetContextTracks)` and `return`s before `mark_doc_dirty()`, `Event::SessionChanged`, `emit_queue()` and the saved-queue diff (lines 503-523). `last_doc` has already been replaced at line 384.
- What goes wrong: if `local_op(SetContextTracks)` is rejected (`reduce` error → toast, no nested `DocumentChanged`), the restored document is never emitted to the UI, never marked dirty (so not persisted until some later mutation) and the saved-queue `SavedQueuesChanged` event is skipped even though the restore reordered/touched the set. The nested path only works because `SetContextTracks` currently cannot fail on a doc with a context; the early return is fragile.
- Fix: run the nested `local_op` after the bookkeeping (or `mark_doc_dirty()`/emit before the `return`).

### 10. A corrupt settings blob is silently replaced with defaults and then overwritten
- `crates/hocket-core/src/core/actor.rs:198` (`Settings::load(&settings_store).unwrap_or_default()`), `crates/hocket-core/src/settings/mod.rs:110-118` (`from_json` error → `Settings::new()` with a log line), `actor.rs:571-573` (next save writes the defaults over the stored document).
- What goes wrong: a partial write / schema surprise in `saved_state("settings")` turns every device-local and synced setting back to defaults on the next start, and the first `save_settings()` (any `SetSetting`, shutdown) destroys the original bytes. design.md/ARCHITECTURE.md: settings "are not rebuildable and get real migrations plus a backup". Synced settings would then be re-broadcast as defaults with a fresh `updated_at` and win LWW on the other devices.
- Fix: on parse failure copy the raw blob to `saved_state("settings.corrupt-<ts>")` (or the backups dir) before continuing, surface an `Event::Error { kind: Storage }`, and don't broadcast synced settings until the user has acknowledged.

### 11. Losing the lease leaves the backend loaded and `backend_key` live; `loaded=false` is set without `stop()`
- `crates/hocket-core/src/core/handlers/playback.rs:247-249` (`else if self.playback.playing { self.set_playing(false) }` on `owns == false`), `crates/hocket-core/src/core/handlers/session.rs:470-475` (`loaded = false`, `backend_key` unchanged, no `backend.stop()`).
- What goes wrong: after a takeover the old owner keeps the decoded stream and output device open (native) or the ExoPlayer item prepared (external) indefinitely; on desktop with `exclusive` output this keeps the device held. Because `backend_key` is not cleared, late reports for that key (`Ready`, `Buffering`, a `Position` from a still-buffering ExoPlayer) still pass the `current()` filter in `on_backend_report` and emit transport/media-session state as if this device were playing.
- Fix: on `owns == false` (and in the render-only branch) call `self.backend.stop()` when `loaded`, and clear `backend_key`/`next`/`awaiting_transition`; keep `doc_key`/`track` for rendering.

## LOW

### 12. `record_play` marks a play as scrobbled when scrobbling is disabled
- `crates/hocket-core/src/core/handlers/playback.rs:796-818`: `allowed && SCROBBLE_ENABLED` decides submission; the `else` branch calls `record_play(…, allowed, …)` where the parameter is `scrobbled: bool` (`db/queries.rs:872-880`). With scrobbling off and `allowed == true`, history says the play was scrobbled. Fix: pass `allowed && enabled` (always `false` in that branch).

### 13. Autoplay engine is moved into a spawned task; a panic there disables autoplay for the rest of the process, and `autoplay_wanted` is never acted upon
- `crates/hocket-core/src/core/handlers/session.rs:531-536` (`self.autoplay.take()`, `autoplay_wanted = true` when in flight), `session.rs:645-647` (`on_autoplay_picks` only clears the flag; never re-requests), `crates/hocket-core/src/core/actor.rs:558-566` (`shutdown` persists the exclusion set only `if let Some(a) = &self.autoplay`). Fix: keep the engine in the actor and hand the task a clone of the settings/exclusion, or re-run `request_autoplay()` when `autoplay_wanted` is set on return; `catch_unwind` around `next_batch`.

### 14. `SeekBy` truncates i64→u32 when the duration is unknown
- `crates/hocket-core/src/core/handlers/playback.rs:377-383`: with `cap == 0` (bare track, `duration_ms` not yet reported) `pos.max(0)` can be `> u32::MAX` and `pos as Ms` wraps to a small number. Fix: `pos.clamp(0, u32::MAX as i64)`.

### 15. `undoable_op` sets `want_playing = true` on a device that does not own transport
- `crates/hocket-core/src/core/handlers/session.rs:226-237`: any Next/Previous/Jump/Play* issued from a controller device flips its own `want_playing`. Later, when that device is granted the lease for any reason (`on_lease_changed`, `playback.rs:243-246`), it starts audio although the user never pressed Play there. Fix: only set `want_playing` when `owns_transport()` or when nobody owns (the branch at `session.rs:463-469` already claims in that case).

### 16. Session document and connect sync-base are persisted in two separate transactions
- `crates/hocket-core/src/core/actor.rs:732-772`: `session:{scope}` then `connect:{scope}` as two `saved_state_set*` calls. A crash between them leaves a document at revision N with a `sync_base` from an earlier flush; on rejoin the engine's behind/diverged classification (design "Resuming is always explicit") uses the stale base and may file the live state as a diverged saved queue or accept it as ahead. Fix: write both keys in one `with_tx`, or store `sync_base` inside the document's `extra`.

### 17. `Command::Scrobble` is a public API that bypasses gating and dedupe
- `crates/hocket-core/src/core/handlers/command.rs:124-129`, `playback.rs:820-841`, `api.rs:1543-1550` ("used only by the core's own scrobbler; exposed for tests"). Any platform/IPC caller can enqueue arbitrary `scrobble(submission=true, played_at=…)` for any track id, skipping the 50%/4-minute rule, the session dedupe (`ScrobbleReached`) and `SCROBBLE_ENABLED`. Fix: gate behind `#[cfg(any(test, feature = "sim"))]` or drop it from `Command`.

### 18. Session-tier undo resurrects saved queues deleted or re-pinned elsewhere (LWW set has no tombstones)
- `crates/hocket-core/src/core/handlers/session.rs:786-800` (`RestoreDocument` → `SessionOp::Replace` with the snapshot's whole `saved_queues`), `session.rs:505-523` (the replaced list is pushed back into the engine's LWW set), `crates/hocket-core/src/session/saved.rs:230-260` (`merge_saved_queues` only compares `updated_at`; a missing entry is treated as "never existed"). Undoing a queue op on device A after device B deleted a saved queue brings the entry back on every device. Fix: exclude `saved_queues` from the snapshot restore (`doc.saved_queues = live.saved_queues.clone()` next to the existing `doc.transport = live.transport.clone()`), or add tombstones.

### 19. `SetShortcut` persists the `shortcuts` setting without emitting `SettingChanged`
- `crates/hocket-core/src/core/handlers/settings.rs:318-345` (`persist_registry` calls `settings.set_value` directly) vs `settings.rs:356-366` (`set_shortcut` emits only `ShortcutsChanged`). The settings screen / `Query::Settings` consumers see a stale `shortcuts` value until restart. `set_action_order` (`settings.rs:368-391`) does emit it. Fix: emit `SettingChanged` for `keys::SHORTCUTS` from `set_shortcut`, or route through `set_setting_value`.

### 20. `on_scrobble_verdict` / `pending_submits` can leak when no engine exists
- `crates/hocket-core/src/core/handlers/playback.rs:757-769`: `pending_submits.insert(..)` then `engine_input(ScrobbleReached)`; `engine_input` returns immediately when `self.engine.is_none()` (`session.rs:158-159`, e.g. between `remove_server` and a new `AddServer`), so the entry is never removed and the scrobble is never recorded. Bounded in practice (one per threshold crossing) but the play is lost. Fix: when `engine.is_none()` fall back to `on_scrobble_verdict(track, started_at, true)` directly.

## Design-vs-implementation notes (not separately rated)

- design.md "Inverses compare-and-swap … undid 487 of 500" holds for ratings/loves (`outbox.execute_cas`, tested in `tests/actor_library.rs:149-194`) but not for playlist ops (#1, #2).
- design.md "Undo on accidental queue replacement carries the outgoing track's position": implemented (`session.rs:229-231`, `session.rs:789-793`) and tested (`tests/actor_playback.rs:114`).
- "Every queue mutation goes through the reducer": holds; I found no path that mutates `SessionDocument` fields outside `reduce`/`Replace`. `Replace` (undo) bypasses the reducer by design.
- Lease/ownership: the actor only drives the backend when `engine.owns_transport()` (`playback.rs:309-330`, `stamp()` at `playback.rs:466-469`); non-owner commands are forwarded as `TransportRequest` and the owner applies them without further checks (`connect/engine.rs:1627-1631`), which matches the design. The gaps are the stale local playback state after ownership changes (#5, #11).
- Gapless: `load_item`'s `transitioned` detection compares `next.track.id == item.track_id` plus `awaiting_transition` (`playback.rs:104-111`); a late `TransitionedToNext` for a stale key is ignored when the document was already reloaded (`playback.rs:600-616`). I could not construct a mis-rebind with the ordering the actor guarantees (engine outputs are handled synchronously inside `engine_input`).
- Scrobble threshold gating (`outbox/scrobbler.rs`, driven from `playback.rs:520-528,560-565`) follows 50%/4 min/30 s with seek exclusion and repeat-one passes; the session dedupe path (`ScrobbleReached` → deferred with grace when no authority, `engine.rs:2688-2705,2880-2898`) does produce a verdict offline.
- Persistence keys `session:{scope}`, `connect:{scope}`, `position:{scope}`, `volume`, `settings`, `autoplay:exclusion` are all `saved_state` rows; `remove_server` deletes the first three by prefix (`servers.rs:219-225`). Crash-restart recovery is only as good as the debounce/heartbeat (#4).
- `RunAction`: alias resolution (`actions/mod.rs:620-626`) happens before applicability; `registry.commands` cannot yield another `RunAction` (`grep` of `defs.rs` finds none), so no recursion. `MediaSessionCommand` → `command_for` never yields `MediaSessionCommand`.
- API input hardening that is fine: `SetVolume` NaN → 1.0, `SetRating` clamped to 5, `MoveQueueItem.to_index`/`PlayTracks.start_index` clamped in the reducer, `PlaylistRemove.indices` bounds-checked, `Query::Stats.period_days.max(1)`, `Page` passed to SQL with a `LIMIT`. Reducer never indexes without a guard (`move_item` checks `visible` before `tracks(..)[index]`).

## HIGH

### 1. `fileRead` / `fileWrite` IPC give the renderer arbitrary filesystem read/write
`desktop/src/main/ipc.ts:118-129`, `desktop/src/preload/index.ts:195-196`

The comment says "File access is limited to paths the user just chose in a dialog", and an `allowed` set is declared, but neither handler ever consults it: `fileRead` does `readFile(path)` for any string, `fileWrite` does `writeFile(path, text)` for any string and only *then* adds the path to the never-read set. A compromised renderer (any XSS in a React view, or a malicious `Toast.actionCommand`-style payload from a hostile server that reaches the page) can read `~/.ssh/id_ed25519`, `credentials.json`, and write `~/.bashrc` / `~/.config/autostart/*.desktop` for code execution outside the sandbox. This is exactly the class of bug the Electron security checklist warns about for `ipcMain.handle` file helpers.

Fix: have `dialogSave`/`dialogOpen` record the chosen path in `allowed` (with a one-shot or short TTL), and make `fileWrite`/`fileRead` reject any path not in the set (`if (!allowed.delete(path)) throw new Error("rejected")`). Alternatively drop these two channels and do the write/read inside `dialogSave`/`dialogOpen` (pass the text in, return the text out) so the renderer never names a path.

### 2. `hocket-art://` serves every file under `userData` and `sessionData`, including `credentials.json` and the core SQLite DB
`desktop/src/main/index.ts:267-274`, `desktop/src/shared/constants.ts:32-35`, CSP at `desktop/src/main/index.ts:283-285`

The doc comment says the scheme "serves artwork files from the cache/data dirs only", but `allowedRoots` is `[cacheDir, dataDir, sessionData, userData]`. `dataDir` is `userData/core` and `credentials.json` is `userData/credentials.json` (`desktop/src/main/credentials.ts:229`), so `fetch("hocket-art://file/" + encodeURIComponent("/home/u/.config/Hocket/credentials.json"))` from page JS returns the safeStorage blobs (see #3 for why those are often decryptable), `main-state.json`, the SQLite mirror (`userData/core/*.db*`), and Chromium's own `sessionData` (Local Storage, Cookies, Session Storage). `connect-src` explicitly allows `hocket-art:` so the renderer can read the bytes, not just display them. The path is renderer-supplied and absolute; nothing restricts it to what `Query.Artwork` returned.

Fix: restrict `allowedRoots` to the image cache directory only (the core's `Query.Artwork` answers live under `cacheDir`), and ideally serve by opaque token: keep a `Map<token, path>` populated from `Query.Artwork` results in main and have `artworkUrl()` reference the token. Also `realpath` the resolved file before the prefix check so a symlink dropped in the cache can't escape.

### 3. Server passwords are persisted with a hardcoded key on Linux desktops Chromium doesn't recognise
`desktop/src/main/credentials.ts:253-262`

`remember()` trusts `safeStorage.isEncryptionAvailable()`. On Linux that returns `true` even when the selected backend is `basic_text`, which Electron documents as the fallback "when the desktop environment is not recognised" (`desktop/node_modules/electron/electron.d.ts:11401-11402`); `basic_text` encrypts with Chromium's fixed key, so the base64 blob in `credentials.json` is trivially decryptable by anything that can read the file (and see #2 for a renderer path to it). Users on sway/Hyprland/i3, over SSH, in containers/CI, or with no keyring daemon get their Navidrome password stored effectively in plaintext, while the code comment and the export UI both claim "OS-encrypted". The `0o600` mode helps only against other local users.

Fix: on Linux, treat `safeStorage.getSelectedStorageBackend() === "basic_text"` as "unavailable" (fall through to the in-memory `volatile` path and surface a one-time warning in Settings), or explicitly opt into it with a visible "store password without OS keyring" toggle. Log the selected backend once at startup.

## MEDIUM

### 4. Quit does not wait for the core to flush; the `before-quit` path never asks it to
`desktop/src/main/core-host.ts:98-100`, `desktop/src/main/index.ts:232-243`, `desktop/src/main/windows.ts:508-512`, `crates/hocket-core/src/core/actor.rs:567-582,732-739`

`NativeCoreHandle.shutdown()` just enqueues `{type:"shutdown"}` on the actor's unbounded channel and resolves immediately; `shutdown()` in `index.ts` then runs `windows.destroyAll()` → `app.quit()`. The actor's `shutdown()` is where the forced session-document flush, `save_position()` and settings save happen (the periodic flush is debounced by `DOC_SAVE_DEBOUNCE_MS`), and it runs on a tokio worker thread that races the process exit. The `setTimeout(app.exit, 3000)` is a hard kill, not a wait. Separately, `app.on("before-quit")` only sets `windows.quitting = true` and never dispatches `shutdown`, so an OS-initiated quit (macOS logout/`app.quit()` from anywhere other than tray/menu) skips the flush entirely. Result: the last few seconds of queue edits, the resume position and unsaved settings are lost on quit.

Fix: make shutdown an awaited round trip: e.g. have the core emit a terminal `stopped` event (or answer a `shutdown` *query*) and resolve `CoreHandle.shutdown()` on it with a bounded timeout; call the same `shutdown()` from `before-quit` (guard with `shuttingDown`, `e.preventDefault()` until the promise settles, then `app.exit`).

### 5. The renderer can crash-loop / dialog-spam the main process through unvalidated IPC payloads
`desktop/src/main/ipc.ts:28-32,74-79`, `desktop/src/main/credentials.ts:243`, `crates/hocket-node/src/lib.rs:66-70`

`ipcMain.on(IPC.dispatch)` validates only `typeof command.type === "string"`, then (a) `credentials.intercept()` dereferences `command.data.url` — `{type:"addServer"}` with no `data` throws a `TypeError`; (b) `NativeCoreHandle.dispatch` calls the addon's `dispatch`, which `Err`s on any shape serde rejects (`{type:"nope"}`) and napi turns that into a thrown JS error. Both throw synchronously inside an `ipcMain.on` listener, i.e. an uncaught exception in the main process (Electron shows the "A JavaScript error occurred in the main process" box). Same for `windowControl` with `{fullscreen:"x"}` / `{alwaysOnTop:1}` — Electron's argument validation throws. The fake core wraps `handle()` in try/catch; the native path doesn't.

Fix: wrap the dispatch handler body in try/catch and log; validate `command.data` is an object (or `undefined` for data-less commands) before `intercept()`; coerce `!!control.fullscreen` / `!!control.alwaysOnTop`. Consider making napi `dispatch` swallow-and-log serde errors so a bad command can never throw across the boundary.

### 6. Any Rust panic on a JS-thread path aborts the whole Electron main process
`crates/hocket-node/src/lib.rs:49-79`, `crates/hocket-node/src/media_session.rs:75-99`

None of the `#[napi]` functions use `#[napi(catch_unwind)]`; napi-derive 3.6.7 only wraps in `catch_unwind` when that attribute is present (`~/.cargo/registry/.../napi-derive-3.6.7/src/parser/mod.rs:892`). The workspace has no `panic = "abort"`, but since Rust 1.81 a panic unwinding out of the generated `extern "C"` trampoline aborts. So a panic in `Core::new` (bad config, DB open), `dispatch_json`, the synchronous part of `query_json`, `MediaSession::set_state`/`set_position`/`publish` (playwire/zbus errors that are `unwrap`ped internally) takes down the app with no JS error, no dialog, and no chance for the core's shutdown flush (#4). Panics inside the actor task are contained by tokio, but the core is then silently dead while the UI keeps dispatching into a closed channel.

Fix: add `#[napi(catch_unwind)]` to every exported fn/method (turns panics into JS errors), and have `Core::with_runtime` wrap the actor future so a panicked actor emits an `Event::Error{kind: Internal}` and the JS side can offer restart.

### 7. Undo toasts stop appearing after 50 undoable mutations
`desktop/src/renderer/store/reducer.ts:540-544`, `crates/hocket-core/src/undo/mod.rs:45,690-694`

The reducer decides an `undoChanged` is "fresh" (and worth a toast) only when `history.length > state.undo.history.length`. `UndoState.history` is capped at `HISTORY_SHEET_LIMIT = 50` newest entries, so once a session has 50 entries the length never grows and every further mutation (shuffle, reorder, rating, queue replace) gets no "… · Undo" toast, violating design.md "Global undo" (every fresh mutation gets one toast). The same happens earlier when the byte budget evicts old entries. `undo.spec.ts` only exercises the first mutation.

Fix: key freshness on the id, not the length: `fresh = top && canUndo && !announcedUndo.includes(top.id) && top.id !== state.undo.history[0]?.id` (the id check already exists; drop the `length` clause). Add a reducer test that pushes 51 `undoChanged` events with fixed-length history and asserts a toast each time.

### 8. "Include server passwords" in config export is a no-op on desktop, and import never restores them
`desktop/src/renderer/views/Settings.tsx:531-532,523-526`, `crates/hocket-core/src/settings/config.rs:3-6,48-57`; no `keystore://` handling anywhere in `desktop/src`

The core, by design, only writes opaque `keystore://hocket/server/<id>/password` references into `ConfigDocument.secrets` and expects "the platform keystore [to] resolve them on import". The desktop `Backup` component writes the emitted document straight to disk and, on import, feeds the file straight back to the core. Nothing in main resolves the references from `ServerCredentialStore` on export or re-adds servers on import, so the checkbox labelled "Include server passwords" produces a file with no usable secrets and a restore on a new machine lands on the setup screen with no explanation. (Design-vs-implementation gap; also user-facing dishonesty about what the file contains.)

Fix: either hide the toggle on desktop until implemented, or implement it in main: on `configExported` with secrets, substitute each reference with `safeStorage`-decrypted passwords only when writing through a dedicated `dialog.exportConfig` IPC (and warn it's plaintext), and on import parse `secrets`, dispatch `addServer` for each and remember them.

### 9. Credential store silently replays a stale password when OS encryption is unavailable, and `retainOnly` can wipe on a transient DB failure
`desktop/src/main/credentials.ts:251-262,272-277`, `desktop/src/main/index.ts:167`, `crates/hocket-core/src/core/actor.rs:530-537,596-598`

(a) When `isEncryptionAvailable()` is false, `remember()` stores the new password only in `volatile` and returns *without* removing the previously persisted entry for the same `url|username`; the next launch replays the old blob (old password) → "Wrong username or password" toast every start with no way to fix it from the UI. `volatile` is never consulted by `replayCommands()` either. (b) At start the core emits `ServersChanged` from `db.servers()`; if that read fails (`Err` branch logs and leaves `server = None`) the event carries `[]` and `retainOnly([])` deletes every stored credential, so a one-off SQLite hiccup permanently logs the user out.

Fix: in `remember()`, always filter the persisted entries for the key before deciding where to store; in `retainOnly`, ignore an empty list that arrives together with `started` (or only prune on `removeServer`, which the code comment already anticipates via `forgetByServer`).

### 10. External deep links / MPRIS `OpenUri` enqueue tracks with no user confirmation
`desktop/src/renderer/App.tsx:97-101`, `desktop/src/main/index.ts:216-224`, `desktop/src/main/media-session.ts:246-247`

### 11. `open-url` is registered after `whenReady`, so macOS cold-start deep links are dropped

### 13. Global shortcuts with modifiers fire inside text fields (Option+Left = "Back")
`desktop/src/renderer/store/keyboard.ts:201-212`, `desktop/src/shared/keymap.ts:40-44`. ### 15. OS media-session position ignores the session clock offset and unknown durations
`desktop/src/main/media-session.ts:294-302`. The ticker uses `Date.now() - p.takenAt` although `takenAt` is session-clock time ("coordinator time when connected", `api.ts:543`), so the MPRIS/SMTC scrubber is off by `clockOffsetMs` when this device is a Connect follower. `Math.min(pos, durationMs ?? pos)` pins the position to 0 when `durationMs` is `0` (unknown), because `??` doesn't treat 0 as missing. ### 16. Toast timers restart for every existing toast whenever the list changes
`desktop/src/renderer/components/Toasts.tsx:140-143`. The effect keys on the whole `toasts` array, so each new toast (or dismiss) re-arms all timers, extending earlier toasts' lifetimes indefinitely under a stream of events. Fix: one timer per toast keyed by id (a `useEffect` inside a `ToastItem`, or a `Map` in a ref).

### 17. Packaged builds silently fall back to the FakeCore, which writes unsanitised ids into the cache dir
`desktop/src/main/core-host.ts:117-119`, `desktop/src/main/fake-core/index.ts:2145-2147,486`. If the addon fails to load (schema mismatch, missing libasound) the app runs the simulator with a dev banner rather than failing loudly; the fake `artworkPath` does `join(cacheDir, "images", `${id}-${s}.png`)` with an unsanitised id (a `../` id writes outside the cache) and `exportNsp` writes to a renderer-supplied `cmd.data.path`. ### 18. Failed artwork lookups are cached for the whole session
`desktop/src/renderer/components/Artwork.tsx:186-191`. A rejected `Query.Artwork` (offline at first render) resolves to `undefined` and that promise stays in the 2000-entry cache, so the cover never appears until restart. Fix: don't cache `undefined`/rejections, or evict on `libraryChanged`/network online.

### 19. Playlist targets are silently truncated at 10 000 tracks

# Android app + UniFFI crate review

Scope: `android/{app,core,playback}`, `crates/hocket-android`, `scripts/build-android-core.sh`, `scripts/gen-bindings.sh`. Core (`crates/hocket-core`) was read only where the Android seam depends on it (dispatch/emit, `AddServer`/probe, `RequestSnapshot`, `MediaSource`). All paths below are repo-relative under `/home/user/hocket`.

## HIGH

### 1. `startForegroundService()` on every process start with no guaranteed `startForeground()` — FGS timeout / not-allowed crashes
- `android/playback/src/main/java/app/hocket/playback/PlaybackServiceConnection.kt:36-38` (`bind()` calls `ContextCompat.startForegroundService(...)` with a plain intent), called from `android/app/src/main/java/app/hocket/HocketApp.kt:38-40` (`Application.onCreate`).
- The doc comment on the class says "started as a plain start", but the code does an FGS start. Media3 1.11.1 `MediaSessionService.onStartCommand` (decompiled from the gradle cache) only calls `startForeground` when a session is playing; for an intent that is neither a media-button nor a custom action it just returns `START_STICKY`. So on Android 12+ (targetSdk 36) every cold launch with nothing playing ends ~10 s later in `ForegroundServiceDidNotStartInTimeException` (ANR on 8–11). Because `PlaybackService.onStartCommand` is `START_STICKY`, once the service is killed the system restarts the process, `HocketApp.onCreate` runs `startForegroundService` from the background and `ForegroundServiceStartNotAllowedException` is thrown, i.e. a restart loop.
- Fix: use `context.startService(...)` (or just `bindService` with `BIND_AUTO_CREATE`, Media3 promotes to foreground itself when playback starts). Only the Media3 `MediaButtonReceiver` should ever FGS-start this service.

### 2. Every `RequestSnapshot` re-fires the credential replay (`Started` is emitted by `emit_everything`)
- `android/playback/src/main/java/app/hocket/playback/CoreHost.kt:95-106` keys the replay on `Event.Started`; `crates/hocket-core/src/core/handlers/command.rs:15` maps `RequestSnapshot` to `emit_everything()`, which emits `Event::Started` (`crates/hocket-core/src/core/actor.rs:593`). `RequestSnapshot` is dispatched from `PlaybackService.kt:70` and `HocketApp.kt:55` (`attach -> client.requestSnapshot()`), so a normal launch dispatches `AddServer(url, user, password)` three times, and again whenever anyone requests a snapshot (service reconnect, `remove_server` -> `emit_everything`).
- Each `AddServer` does a network probe and `install_server` (`crates/hocket-core/src/core/handlers/servers.rs:135-200`): new `LibrarySync`, `SetCredential`, `ServersChanged`, `maybe_start_sync`, `register_job_runners`. Also interacts with #3.
- Fix: replay once per core start. Either key on a local `replayedForThisCore` flag (`if (_credentialsReplayed.value) return@collect` before replaying) or have the core emit a distinct `Started` only from `start()` and a `Snapshot` event from `RequestSnapshot`.

### 3. Sign-out from Settings resurrects the server with full credentials
- `android/app/src/main/java/app/hocket/ui/screens/settings/SettingsScreen.kt:189` dispatches `RemoveServer` without touching the keystore store (the setup screen at `ServerSetupScreen.kt:151` does remove it first). `remove_server` (`servers.rs:210-230`) clears state and calls `emit_everything()`, which emits `Started{servers: []}` **before** `ServersChanged{[]}` (`actor.rs:593-598`).
- `CoreHost.replayCredentials`: `Started` with `known.isEmpty()` -> `toReplay = store.all()` -> `AddServer(A, password)` is dispatched (CoreHost.kt:100-103); the following `ServersChanged([])` then wipes the store (CoreHost.kt:111). The queued `AddServer` probes and re-installs the server with a fresh token, restarts sync and re-opens a session. Net effect: "Remove server" leaves the user authenticated for the rest of the process lifetime, and on the next launch the server row exists in the DB but has no stored password (setup screen with `existing` pre-filled).
- Fix: in the `Started` branch skip replay when `_credentialsReplayed.value` is already true (fixes #2 too), and make `SettingsScreen` remove the credential before dispatching `RemoveServer` (or move the removal into one helper used by both screens).

### 4. Offline launch: replayed `AddServer` fails the probe, server never gets an API client, downloads are unplayable
- Design (`docs/design.md`: "keeps working when the network doesn't"). At `start()` the persisted server is restored without an API (`actor.rs:527-537`). The only way it gets one on Android is the keystore replay -> `add_server` -> `spawn_probe` -> `on_probed` (`servers.rs:70-79`, `247-262`); `probe` fails on any `ping` failure (`crates/hocket-core/src/subsonic/probe.rs:40-41`) and `probe_failed` just toasts (`servers.rs:305-317`), dropping the pending server. `media_source_for` needs `self.api()?` even for `file://` sources (`handlers/playback.rs:23-24`), so with no network at launch nothing, including pinned downloads, can play; the UI still shows the shell because `hasLogin` only checks the keystore (`AppRoot.kt:124`).
- Nothing retries: `set_network_state` (`servers.rs:598-610`) only flushes the outbox; `probe_server` needs an existing `client`, which the pending path never installed. Ironically the only "retry" today is bug #2.
- Fix (core + Android): install the client immediately when the persisted server id matches (capabilities from the DB), mark `reachable=false`, and re-probe on `SetNetworkState`; or on Android re-dispatch `AddServer` when `NetworkKind` goes Offline -> online while `servers[0].reachable == false`.

## MEDIUM

### 5. Transient Keystore failure permanently deletes the stored password
- `android/playback/src/main/java/app/hocket/playback/ServerCredentialStore.kt:82-92, 99-103`: any `Exception` from `Cipher.init/doFinal` (including `KeyStoreException`/`ProviderException` seen on some OEMs right after boot, during `keystore2` restarts, or after OS upgrades) is treated as "key rotated" and `get()` removes the entry. The user is silently logged out and must re-enter the password; with #4 the app is also unusable offline.
- Fix: only delete on `AEADBadTagException` (or when `ks.containsAlias(ALIAS)` is false); otherwise return `null` without removing, and surface a "needs re-login" state rather than destroying data.

### 6. `all()` treats `<key>#name` entries as credentials and deletes them
- `ServerCredentialStore.kt:94-97`: `prefs.all.keys` includes `"url|user#name"` (written at :110). `split("|", limit = 2)` yields `("url", "user#name")`; `get()` reads the plaintext name string, `decrypt()` fails (no `:` or bad Base64) -> logs "credential undecryptable" and **removes** the name entry. So every `CoreHost.replayCredentials` run wipes all server names and logs a spurious warning per server. Not currently user-visible on Android because `ServerSetupScreen` always stores `name = null`, but the store is also what the core relies on ("app replays AddServer from here").
- Fix: `prefs.all.keys.filter { !it.contains('#') }`, or store names under a separate prefs file / a single JSON blob.

### 7. Backup/data-extraction rules ship the device id and the whole library mirror
- `android/app/src/main/AndroidManifest.xml:9-11`, `res/xml/backup_rules.xml`, `res/xml/data_extraction_rules.xml` exclude only `hocket/cache` and `hocket/downloads`. The SQLite mirror lives at `files/hocket/hocket.sqlite` (+ `hocket/backups`) (`crates/hocket-core/src/core/actor.rs:186-190`), so it is backed up (often > the 25 MB auto-backup quota, which makes the entire backup fail so nothing is preserved). Both `hocket-core.xml` (`deviceId`, `CoreHost.kt:150-157`) and `hocket-credentials.xml` (server URL + username in plaintext keys, AES-GCM ciphertext) are included. A restore/transfer to a second device yields two devices with the **same** Connect `deviceId` (lease/epoch/election confusion), and the ciphertext is undecryptable there (Keystore keys do not transfer) so `get()` just deletes it.
- Fix: exclude `sharedpref` `hocket-core` and `hocket-credentials`, and `file` `hocket/hocket.sqlite*`/`hocket/backups`, from both cloud-backup and device-transfer; regenerate `deviceId` when restored (e.g. `BackupAgent`/`onRestore` marker or store it under an excluded prefs file).

### 8. Stream URLs carry `t`/`s` auth; ExoPlayer allows https->http redirects and cleartext is enabled globally
- `MediaSource.url` is documented as "auth in query" (`crates/hocket-core/src/api.rs:1017`, built by `wire_credential` at `servers.rs:617-627`). `android/playback/src/main/java/app/hocket/playback/ExoBackend.kt:262-266` sets `setAllowCrossProtocolRedirects(true)`, so an `https://` server (or a reverse proxy / captive portal) that redirects to `http://` re-sends the token+salt in cleartext; the token is replayable for any Subsonic call. `android:usesCleartextTraffic="true"` (manifest :17) with no `network_security_config` means every HTTP host is allowed, not just the user's own server.
- Fix: drop `setAllowCrossProtocolRedirects(true)` (default false); add a `network_security_config` that permits cleartext only when the user explicitly entered an `http://` URL (or warn in `ServerSetupScreen`); longer term use headers instead of query auth once the core supports it.

### 9. Redundant exported legacy `androidx.media.session.MediaButtonReceiver`
- `android/playback/src/main/AndroidManifest.xml:25-31`. Media3 already declares its own `androidx.media3.session.MediaButtonReceiver` (confirmed in the media3-session 1.11.1 AAR manifest), which only FGS-starts the service for a PLAY key when nothing is playing. The legacy receiver is exported with a `MEDIA_BUTTON` filter, so any app on the device can `sendBroadcast` an explicit `MEDIA_BUTTON` intent with an arbitrary `KeyEvent`; the legacy receiver resolves the service through the `MediaBrowserService` filter and `startForegroundService`s it with that key, which (a) starts playback on demand from third-party apps and (b) for a non-play key with nothing playing hits the same FGS timeout crash as #1.
- Fix: delete the `<receiver>` element; Media3 handles media buttons.

### 10. Release builds silently fall back to `FakeCore`
- `android/playback/src/main/java/app/hocket/playback/CoreHost.kt:69-79`: any exception from `NativeCore.create` (DB open failure, corrupt `hocket.sqlite`, JNA load error) swaps in `FakeCore`. The banner is gated on `BuildConfig.DEBUG` (`AppRoot.kt:133`) and `hasLogin` is short-circuited for the fake kind (`AppRoot.kt:124`), so a release user with a broken data dir sees a fake library with fake playback and no error, and their real state is never repaired.
- Fix: in release, surface a fatal error screen (with a "reset data" action) instead of the fake; keep the fake only for `forceFake`/debug.

### 11. `NativeCore.close()` races the core's shutdown and blocks the main thread
- `android/core/src/main/java/app/hocket/core/NativeCore.kt:55-58` dispatches `Shutdown` and immediately calls `core.close()`, which drops the last `Arc<HocketCore>` -> `Inner` -> the owned tokio `Runtime` (`crates/hocket-core/src/core/mod.rs:293-296, 332-370`). The actor only flushes persistence/position in `shutdown()` after it dequeues `Shutdown` (`actor.rs:360-377`); dropping the runtime cancels tasks that are not mid-poll, so whether the flush happens is a race. `Runtime::drop` also joins the worker threads, so `PlaybackService.onDestroy` (main thread) blocks for as long as the actor's current message takes (a sync batch, a DB backup).
- Fix: add an FFI `shutdown()` that sends `Shutdown` and awaits an acknowledgement (oneshot from `Actor::shutdown`) with a timeout, call it off the main thread, then free.

### 12. Event bus drops events under back-pressure, including `Started`/`ServersChanged`
- `NativeCore.kt:27, 39`: `MutableSharedFlow(extraBufferCapacity = 512)` + `tryEmit` with default `SUSPEND` overflow: when any subscriber is slower than the core (sync progress bursts, `JobsChanged`, per-tick `TransportChanged`, while the main thread is busy composing), `tryEmit` returns false and the event is **dropped**, whichever type it is. Dropping `Started` leaves `credentialsReplayed` false forever (Loading screen); dropping `SessionChanged` leaves the queue UI stale; dropping `Backend` commands desyncs ExoPlayer from the core.
- Additionally `CoreHost.acquire` (`CoreHost.kt:82-84`) launches the replay collector on `Dispatchers.Default` and dispatches `Start` before that coroutine has necessarily subscribed; there is no replay, so a fast `Started` can be missed on a cold start.
- Fix: back the seam with an unbounded `Channel` (`Channel.UNLIMITED` -> `receiveAsFlow()`), or at least `BufferOverflow.DROP_OLDEST` for high-frequency types only; subscribe before dispatching `Start` (e.g. `scope.launch(start = CoroutineStart.UNDISPATCHED)`).

### 13. Idle stop never fires; the process lives forever after the task is swiped away
- `HocketApp.kt:40` binds with `BIND_AUTO_CREATE` from `Application.onCreate` and nothing ever calls `PlaybackServiceConnection.unbind()` (only call site is the class itself). `PlaybackService.scheduleIdleStop` requires `boundClients == 0` (`PlaybackService.kt:98`), which is therefore never true, and `onTaskRemoved -> pauseAllPlayersAndStopSelf()` (`:129-131`) cannot destroy a service that the same process keeps bound. Result: after the user closes the app, the tokio runtime (250 ms tick loop), `NetworkMonitor`, `BatterySaverMonitor` and ExoPlayer stay alive until the OS kills the process, at which point #1's restart loop kicks in.
- Fix: bind from the Activity (or `ProcessLifecycleOwner` `onStart`/`onStop`), unbind when no UI is visible and nothing is playing, and count only UI binders.

## LOW

### 14. Kotlin exception inside the event callback panics the Rust actor
- `NativeCore.kt:31-41` only catches `SerializationException`; any other `Throwable` from `onEvent` (OOM while decoding a large snapshot, a `Log` failure) propagates through `uniffiTraitInterfaceCall` as `UNEXPECTED_ERROR`; uniffi 0.29.5 turns that into `panic!("Callback interface failure")` (`uniffi_core/src/ffi_converter_traits.rs:396-398`) on the actor task (`Core::emit`/`Actor::emit` call sinks synchronously, `core/mod.rs:388-393`). The actor task dies silently; subsequent `dispatch` logs `ShutDown` errors.
- Fix: `catch (t: Throwable)` in `onEvent`; consider `catch_unwind` around `self.0.on_event(json)` in `crates/hocket-android/src/lib.rs:35-41`.

### 15. Undecodable-event log line can contain a stream URL with token+salt
- `NativeCore.kt:36`: kotlinx `JsonDecodingException.message` appends `JSON input: <snippet>`; for a `Backend.Load` event that snippet is the stream URL including `t`/`s`. Only on schema drift, but logcat is readable by `adb`/bug reports.
- Fix: log `event` type only (`e.message?.substringBefore("JSON input")`).

### 16. Failed login leaves a stale credential that is replayed forever
- `ServerSetupScreen.kt:86-87` saves to the keystore **before** the core verifies the login; on probe failure nothing removes it (the prune only runs on `ServersChanged`). With `known.isEmpty()` (`CoreHost.kt:100`) every subsequent launch dispatches `AddServer` to the bogus URL/password and shows "Couldn't reach the server"/"Wrong username or password". Also, since the core is single-server, several stale entries are replayed back-to-back, each `unload()`ing the previous one.
- Fix: save the credential on the first `ServersChanged` that contains the server (or on `Started` after success), and remove it on `Event.Error{kind: Auth}` for that server.

### 17. Password held in `rememberSaveable`
- `ServerSetupScreen.kt:68`: the password field state is saved into the Activity saved-instance Bundle (handed to `system_server`, survives process death in the recents task record).
- Fix: `remember { mutableStateOf("") }` for the password.

### 18. `PlaybackService.onBind(ACTION_BIND_CORE)` is exposed to other apps
- Service is `exported="true"` (required for Media3) and `PlaybackService.kt:107-114` returns `LocalBinder` for any caller with that action and bumps `boundClients`. A third-party app cannot call the Kotlin getters across processes, but it can bind to keep the service (and core) alive indefinitely and skew the idle logic.
- Fix: check `Binder.getCallingUid() == Process.myUid()` (or a signature permission) before returning the local binder; otherwise fall through to `super.onBind`.

### 19. Location permissions declared but never requested; SSID hash path is dead on API 31+
- `android/playback/src/main/AndroidManifest.xml:12-13` declares `ACCESS_COARSE/FINE_LOCATION`; no `requestPermission`/`POST_NOTIFICATIONS` request exists in the app (grep), so `ssidHash` (`Monitors.kt:66-77`) always returns null and the per-network profile id collapses to `"wifi"`; on API 31+ the callback would also need `FLAG_INCLUDE_LOCATION_INFO`. Play review flags unused location permissions.
- Fix: either request the permission behind the "per-network transcoding" setting or drop the permissions until then.

### 20. `build-android-core.sh` NDK discovery masks failures; toolchain side effects
- `scripts/build-android-core.sh:12`: `export ANDROID_NDK_HOME=$(ls -d "$ANDROID_HOME"/ndk/* | sort -V | tail -1)` - `export` hides the non-zero status, so with no NDK installed `ANDROID_NDK_HOME` is empty and cargo-ndk fails with an unrelated message despite `set -euo pipefail`. Lines 18-21 `cargo install`/`rustup target add` mutate the developer toolchain implicitly. The release profile (`Cargo.toml:56-59`) has no `panic = "abort"`/`strip`; stripping relies on cargo-ndk defaults.
- Fix: `NDK=$(ls -d ... ) || { echo "no NDK" >&2; exit 1; }`; print instructions instead of installing; set `strip = true` explicitly for the cdylib profile.

### 21. `ExoBackend.onPlayerError` reports key `"?"` and `SetNext` without a current item promotes the follow-up to current
- `ExoBackend.kt:150` sends `BackendReport.Error("?", ...)` when the playlist is empty (e.g. error during `prepare` after `Stop`), which the core cannot correlate. `ExoBackend.kt:168-171` `SetNext` after `Stop` (`mediaItemCount == 0`) makes the "next" source the current item, so a later `Play` plays it under the wrong key.
- Fix: skip the report when there is no current key (or use the last loaded key); ignore `SetNext` when `mediaItemCount == 0`.
